## 3. 方法

```
release .onnx ─┐
               ├─ onnxslim ─> TFDL 转换（std/mean 内嵌，检测头 stop/avoid）─> <name>.fb（FP32）
release .pt ───┘                └─ torch-cpu 校准 + per-channel 量化 ────────> <name>.quant.fb（INT8）
```

- **转换**：检测/分割/姿态/OBB 走 `example/yolo_tfdl_common.py`（从 ONNX 拓扑自动识别预测头、DFL、NMS 边界），
  分类/ReID/语义走 `onnx2tfdl.py`；语义模型输出 ArgMax 整数标签，先截到 logits 再转换。
- **量化**：`--calibration-backend torch-cpu`，32 张 COCO val 图（`[0,255]` 输入、内嵌归一化），
  MinMax 取范围 + per-channel 权重量化。实测比 `sdk-cpu` 快约 3×，且 AP 更好（yolo11s 0.447→0.495）。
- **Benchmark**：`ConvertTools/python/NPU40TQuantize/bench_tfdl`，batch=1、单线程、warmup 5 + 20 次平均，
  `Core: [-1]`（等价单核，见第 4 节），报告 `mean_ms`。
- **精度**：COCO2017 val2017 每 10 张取 1（300 张）letterbox 640 → NPU → `ultralytics` NMS → `pycocotools`；
  同一子集用 ONNX Runtime FP32 做对照。ReID 用 Market-1501 全量（query 3368 / gallery 13115，
  按标准协议剔除同 ID 同摄像头）。

## 4. NPU core 数对 INT8 单帧延迟的影响

同一批 INT8 模型，只改 `runconfig` 里的 `Core` 列表（`[-1]` 为运行时默认）：

| 模型 | [-1] 默认 | [0] 1 core | [0,1] 2 core | [0,1,2,3] 4 core |
|---|---|---|---|---|
| yolo11n | 20.47 | 21.04 | 25.83 | 30.25 |
| yolo11s | 32.11 | 32.17 | 34.42 | 39.58 |
| yolo11x | 130.19 | 125.38 | 112.14 | 104.60 |

- 小模型（n/s）：单核最快，多核拆分只增加同步开销（n: 20.5 → 30.3 ms）。
- 大模型（x）：多核有收益，4 核比单核快约 16%（130.2 → 104.6 ms）。
- 本报告全部数据均按 **1 个 NPU core、batch=1、单线程** 测量，可横向比较。

## 8. 默认不支持的模型

| 类别 | 模型数 | 原因 |
|---|---|---|
| `yolo26*-depth` | 5 | depth 头含 `Exp/Log` + `ConvTranspose`，SDK 原生 `Quantize` 退化到 30 分钟以上 |
| YOLOE | 17 | LRPC 头 + 文本分支，同上；`yoloe-26*-pf` 构图阶段还会 `double free` |
| `yolov8*-worldv2` | 5 | SDK 量化器对 4D 注意力 MatMul 插入 rank-2 transpose 崩溃 |
| `yolov9e` / `yolov9e-seg` | 2 | 转换器未实现 `ReduceSum` |
| `yolov3-tinyu` | 1 | 转换器未实现非常量 `Pad` |
| 公开 ultralytics 缺模块 | 26 | `*-reid-market`、`*-s3d`、`*-stereo3ddet-siamese`、`*-human`、`*-world`、`yolo_nas_*` |
